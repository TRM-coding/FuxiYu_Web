# Design

## Context

- `AdminLogs` 当前用 antd `Select` 保存单个 `targetType`，`listOperationLogs` 用 `URLSearchParams.set` 写入每个键，因此数组会被字符串化成逗号分隔的单个值。
- `User` 个人资料页和 `ManageUser` 的两个编辑入口都可能把清空后的年份转成 `null` 后提交；Ctrl 会丢弃 `null`/空串，造成 400 或静默不生效。
- `trackAnnouncementSend` 只把“跟踪集合中已返回且离开 sending”的公告计入完成；已删除公告永远不会返回，轮询没有终止条件。
- 本仓库为 spec-driven OpenSpec 项目，语言 zh-CN；本次只改 Web，不修改 Ctrl/Node、不提交、不归档。

## Goals / Non-Goals

**Goals:**

- 目标类别支持复选多选、全选和零项即全部，并发出可被 Ctrl 按多值解析的重复查询参数。
- 保持其他筛选 AND、统计窗口、分页参数与分页更新语义不变。
- 毕业年份继续保持不可清空，所有可达编辑入口在提交前阻止空值并给出明确反馈。
- 删除发送中公告后，前端在有限宽限期内识别持续缺失，停止轮询并显示不可确认状态。

**Non-Goals:**

- 不新增 Ctrl 清空毕业年份能力，不修改数据库 nullable 约束。
- 不实现“删除即取消投递”，不修改后台投递线程或删除接口状态守卫。
- 不改变统计范围、分页大小选项、周次导航或日志详情展示。
- 不新增日志目标类别的后端枚举或权限。

## Decisions

### 1. 目标类别使用受控数组与 Checkbox.Group

`AdminLogs` 用 `targetTypes: string[]` 替换单个 `targetType`，初始为 `[]`。目标类别区域改为独占一行的 `Checkbox.Group`，选项沿用现有九类；“全选”按钮把所有类别写入数组。零项和全部勾选均表示“全部”，不传 `target_type`，包括历史未知类型；页面提示“未选择 = 全部”，不渲染清空按钮。仅部分勾选时传入所选类型。

选择“独占一行”而不是压缩原五列，是因为九个复选项在窄列中会严重换行并挤压时间范围；独占一行同时改善 320px 布局。重置按钮保持既有“重置全部筛选”语义，不作为目标类别专用清空按钮。

### 2. 查询序列化支持数组重复参数，标量行为不变

在 `operation_log_api` 增加统一的查询参数写入函数：数组逐项 `append`，标量与现有 `set` 行为一致，空数组、`undefined`、`null`、空串全部跳过。`listOperationLogs` 与 `getOperationLogStats` 共用该函数，保证现有单值调用完全兼容。

不采用逗号拼接：后端契约是重复 `target_type` 参数，逗号值会被当成一个未知类别；也不在页面层手写 URL，以免绕过统一超时和错误处理。

### 3. 毕业年份用共享纯函数校验，入口层阻止提交

新增 `normalizeGraduationYear(raw)`：空值返回 `empty`，非整数返回 `invalid`，否则返回数值；各入口原有输入范围保持不变。`User` 在“修改”时先校验，空值显示行内错误并直接返回；只有数值变化才调用 `updateUser`。`ManageUser` 的展开行编辑器在年份被清空时显示行内错误并禁用保存；卡片编辑器在保存前检查“原值非空、当前为空”，显示 `message.error` 并阻止整个保存，避免只提交用户名而静默丢掉年份。

对“原本就没有年份且保持为空”的情况不视为修改，不产生字段；绝不把空值转成 `null` 传给接口。`updateUser` API 本身保持通用，不在 API 层吞字段，以免掩盖其他调用方错误。

### 4. 公告轮询增加持续缺失宽限期与 unknown 终态

`trackAnnouncementSend` 增加 `missingGraceMs`（默认 15000ms）。每次响应计算跟踪集合中缺失的 id：若缺失首次出现则记录时间；若后续响应恢复完整则清除；若持续缺失超过宽限期，则停止轮询并调用 `onUnknown({ total, unknownIds, knownIds, done, success, fail })`。缺少宽限期会让“刚发起、状态接口尚未可见”被误判；无终止条件则造成 Q49 的无限轮询。

`Announcements` 新增 `sendProgress.unknown` 分支：显示“状态不可确认”，说明有公告已删除或无法查询，展示未知条数，不显示“已完成”、不汇总成功/失败、不声称已取消；同时刷新草稿和已发送列表。已知公告的进度仍可显示，但不会把未知项计入成功或完成。

### 5. 测试分层

- API 序列化单测直接 mock `fetch`，断言 URL 中重复 `target_type`、单值兼容和空选择不传。
- `AdminLogs` 组件测试覆盖多选、全选、全不选、与其他筛选 AND、分页/统计请求不变。
- `User` 与 `ManageUser` 组件测试覆盖清空年份的反馈、未调用更新接口，以及有效年份正常提交。
- `announcementSend` 纯函数测试覆盖持续缺失转 unknown、短暂缺失恢复、部分缺失；组件测试覆盖 unknown 文案且不出现成功/取消。

## Risks / Trade-offs

- [Ctrl 若只读取第一个 `target_type`] → 本变更遵守“重复参数”契约；联调时需确认 Ctrl 已按多值解析，Web 不做逗号兼容以免掩盖契约偏差。
- [15000ms 宽限期对极慢状态接口可能误判] → 只对持续缺失生效，任何一次恢复都会重置；文案使用“已删除或无法查询”，不武断断言删除。
- [停止轮询后其余公告仍在后台发送] → 这正是用户决定“不取消投递”的结果；页面明确显示不可确认并刷新列表，不伪造终态。
- [卡片编辑阻止整个保存] → 用户需先恢复年份或重置再保存其他字段；这是避免部分更新静默丢字段的刻意取舍。
- [既有测试固化了“空串被丢弃”] → 组件层已不再产生空串请求；不修改 Ctrl 既有测试，Web 仅新增入口回归。
