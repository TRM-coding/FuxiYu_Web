# Design

## Context

`deriveDeletedMountState` 是桌面状态列与移动卡片共用的纯函数，输入列表记录与当前页 `usageById` 项，输出状态键和中文文案；`renderUsageCell` 独立渲染成功样本、等待状态或稳定错误文案。当前已提交实现按“无挂载 → 已清理且成功 → `not_found` → `permission_denied` → 已清理 → 升级清理/mount 保留”判断，已清理记录的历史路径采集错误会先于“已清理”命中。

主规格 `frontend--page-deleted-containers` 共 17 条需求。逐条核对其场景后，只有“按用量结果派生挂载实际状态”和“移动端 Mount 复制与用量状态”中的“已清理与无挂载不采样”场景与目标优先级冲突；页面入口、主流程、构建归属、长期恢复超限、root 凭据、分页上下文、当前页采样、逻辑大小与测量时间、有界轮询、旧接口兼容、表格层级、移动卡片布局、移动详情展开、移动分页与轮询、用量不改变门禁等要求无需改变。

## Goals / Non-Goals

**Goals:**

- 用单一有序判断固定挂载状态优先级，桌面与移动共享同一结果。
- 已清理 + 成功（含 0 B）→“可能存在残留”；已清理 + 任意失败或 pending →“已清理”。
- 采集列继续独立显示采集错误；无挂载不进入请求。
- 保持既有请求范围、轮询、取消、分页、恢复/清理门禁与确认流程不变。

**Non-Goals:**

- 不改变 Ctrl/Node 契约、错误码白名单或请求体。
- 不新增状态文案、颜色、接口字段、数据库字段、权限或 WSS。
- 不把采集结果用于恢复/清理授权、按钮禁用或提交参数。
- 不在本次规划中修改主规格、代码或提交。

## Decisions

1. **有序守卫链，先命中先返回。**
   在 `deriveDeletedMountState` 中按固定顺序判断：`mount_path` 为空 → 无挂载；已清理且 `usage.status === 'success'` → 可能存在残留；已清理 → 已清理；`error === 'not_found'` → 目录不存在；`error === 'permission_denied'` → 无权限；`cleanup_escalation` → 升级清理；否则 mount 保留。
   理由：已清理来自列表事实，是生命周期状态；`not_found`/`permission_denied` 只是历史路径采样得到的观测，不能反向覆盖生命周期。替代方案（保留错误优先）会让同一行状态与列表中的“已清理”事实矛盾，已拒绝。

2. **成功判定包含 0 B。**
   `normalizeMountUsageItem` 已接受 `bytes=0` 的成功样本；派生只判断 `status === 'success'`，不按字节数分流。
   理由：成功读取路径本身说明目录可达，0 B 只表示逻辑大小为 0，仍可能存在残留；采集列照实显示 0 B，不夸大为已占用。替代方案（0 B 视为已清理）会丢失“路径仍存在”的信号，已拒绝。

3. **状态列与采集列分层。**
   `statusTag` 只消费派生状态；`renderUsageCell` 保持现有成功/等待/错误的独立展示。已清理记录的 `not_found`/`permission_denied` 在状态列为“已清理”，在采集列仍为“统计不可用（目录不存在）”“统计不可用（无权限读取目录）”。
   理由：两列回答不同问题，状态列回答记录处于什么生命周期状态，采集列回答历史路径这次测量得到什么。替代方案（状态列覆盖采集列，或反过来隐藏错误）会丢失诊断信息，已拒绝。

4. **错误状态只对未清理记录生效。**
   `not_found`/`permission_denied` 分支位于 `cleaned` 之后，仅在记录未清理时显示“目录不存在/无权限”；未清理记录的 pending、缺项、Node 不可用等其他结果继续回退“mount 保留”或“升级清理”。
   这保留原有“仅明确错误才覆盖列表事实”的保守原则，只是不再覆盖已清理事实，也不改变无挂载和请求范围。

5. **测试按优先级集中覆盖，只改冲突断言。**
   在 `mountUsage.test.js` 覆盖无挂载、已清理成功（正数与 0 B）、已清理错误、已清理 pending/其他失败、未清理错误、未清理回退七类分支；在桌面、移动与清理/恢复集成测试中验证渲染和采集列错误仍可见。
   理由：优先级是纯函数契约，集中断言比在多处 JSX 测试重复更容易发现回归。只更新与旧顺序冲突的断言，保留无挂载不采样、轮询、分页、门禁和错误文案用例；替代方案（只改移动断言或只改快照）会留下桌面和单元层冲突，已拒绝。

## Risks / Trade-offs

- [状态“已清理”与采集列“目录不存在”同屏，可能被读成矛盾] → 两列语义固定为生命周期与测量结果，规格场景明确要求二者同时显示；不改文案，避免引入新术语。
- [错误从状态列消失，降低目录异常的一眼可见性] → 采集列仍显示“统计不可用（目录不存在）/（无权限读取目录）”，信息未丢失，只是不再覆盖生命周期状态。
- [已清理 + 0 B 仍称“可能存在残留”可能被误解为一定有数据] → 文案保持“可能”，采集列显示真实 0 B；规格明确不把 0 B 说成已占用或一定有残留数据。
- [旧测试断言仍期待错误状态] → 逐项更新 `mountUsage.test.js`、桌面与清理/恢复集成测试；移动断言已有同方向改动，实施时核对，避免遗漏或覆盖无关改动。
- [工作区已有部分相关改动] → 实施时先核对现有差异，在其基础上完成，不回退、不提交；本次规划不触碰代码。

## Migration Plan

1. 调整 `deriveDeletedMountState` 的分支顺序，保持函数签名和返回结构不变。
2. 核对 `renderUsageCell` 与状态列调用点，确认采集列错误展示不受影响。
3. 更新冲突的单元与集成断言，新增 0 B、已清理错误、未清理错误三类优先级的定向断言。
4. 运行定向 Vitest、相关 ESLint 与 `openspec validate --strict`；回滚只需恢复派生顺序，无数据迁移。
